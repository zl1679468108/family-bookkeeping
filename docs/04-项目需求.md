## P2 — 下一迭代（已完成）

### P2-1 收据上传 ✅

**定位**：为交易记录附加收据照片，提升记账凭证感，方便日后核对。

**痛点**：用户需要翻找相册或邮件来回忆某笔消费的详情，纯文字记录缺乏视觉佐证。

---

#### 核心功能

| 功能点 | 描述 | 优先级 |
|--------|------|--------|
| 上传收据 | 新增/编辑交易时可拍照或选择图片，前端压缩至 ≤300KB 后上传 | P0 |
| 查看收据 | 交易列表中显示收据小图标（📎），点击弹窗查看大图 | P0 |
| 替换收据 | 编辑交易时可更换已有收据，旧文件自动删除 | P1 |
| 删除收据 | 编辑交易时可移除收据，确认后删除存储文件（使用 ConfirmDialog） | P1 |
| 多图收据 | 单笔交易暂只支持一张收据，避免复杂度膨胀 | P2（不做） |

#### User Stories

- As a 记账用户, I want 添加交易时拍照/上传收据 so that 日后能核实消费细节
- As a 记账用户, I want 交易列表上能一眼看出哪些有收据 so that 快速定位需要核对的记录
- As a 记账用户, I want 点击收据图标查看大图 so that 无需下载即可查看完整信息
- As a 记账用户, I want 删除交易时收据一并清理 so that 不浪费存储空间

---

#### 交互流程

```
新增交易页                     编辑交易页
  ┌──────────┐                  ┌──────────┐
  │ 金额输入  │                  │ 金额输入  │
  │ 分类选择  │                  │ 分类选择  │
  │ ...      │                  │ ...      │
  │ [📷 拍照] │ ← 点击触发       │ 已有收据  │ ← 显示缩略图
  │ [🖼 相册] │ ← 点击触发       │ [替换] [删除] │
  └──────────┘                  └──────────┘
        │                              │
        ▼                              ▼
  前端压缩(≤300KB)              替换→上传新图+删旧图
        │                       删除→ConfirmDialog→删存储
        ▼
  POST /api/transactions/:id/receipt
        │
        ▼
  后端 → Supabase Storage
        │
        ▼
  返回完整 URL，前端即时展示
```

---

#### 后端 API 设计

| 端点 | 方法 | 说明 |
|------|------|------|
| `/api/transactions/:id/receipt` | `POST` | 上传收据（multipart/form-data） |
| `/api/transactions/:id/receipt` | `DELETE` | 删除收据（软删除 storage 文件 + 清空 image_url） |

**POST 请求**：`multipart/form-data`，字段名 `file`

**POST 响应**：
```json
{
  "code": 0,
  "data": {
    "image_url": "https://xxx.supabase.co/storage/v1/object/public/receipts/xxx.jpg",
    "relative_path": "receipts/user_abc/2026/06/uuid.jpg"
  }
}
```

**DELETE 响应**：
```json
{
  "code": 0,
  "data": { "message": "ok" }
}
```

**后端处理流程**：
1. 验证交易存在且当前用户有权限（所属账本成员）
2. 接收文件，校验类型（jpg/png/webp）和大小（≤5MB 原始）
3. 生成存储路径：`receipts/{user_id}/{year}/{month}/{uuid}.{ext}`
4. 调用 Supabase Storage SDK 上传，设置 `content-type` 和 `cache-control`
5. 将 `relative_path` 写入 `transactions.image_url`
6. 返回拼接后的完整 URL

---

#### 存储路径规范

```
bucket: receipts (public)
路径:   /{user_id}/{year}/{month}/{uuid}.{ext}
示例:   /receipts/user_abc123/2026/06/a1b2c3d4.jpg

规则:
  - user_id: 上传者 auth.id（非 book 维度，保证跨账本可访问）
  - year/month: 基于上传时间，便于人工清理
  - uuid: crypto.randomUUID()，防冲突
  - ext: jpg/png/webp，统一转 jpg（前端压缩时处理）
```

---

#### 前端关键实现

| 环节 | 方案 |
|------|------|
| 图片选择 | `<input type="file" accept="image/*" capture="environment">` 支持拍照+相册 |
| 压缩 | 使用 `canvas` 缩放至长边 1200px，quality 0.7，目标 ≤300KB |
| 上传 | `axios.post(url, formData)` 带进度条（可选） |
| 缩略图 | 列表页用小图标 📎 标识；编辑页显示 80×80 缩略图 |
| 大图查看 | 独立的 Modal，`<img>` 撑满可用空间，点击空白关闭 |
| 删除确认 | ConfirmDialog："确定移除收据？移除后无法恢复" |

---

#### 技术边界

| 维度 | 决策 |
|------|------|
| 是否新建表 | **否** — 复用 `transactions.image_url`（varchar），存相对路径 |
| 是否新建模块 | **否** — 收据上传作为 transactions 模块的补充路由 |
| Storage Bucket | 新建 `receipts` bucket（public 访问），策略：`authenticated` 可上传/删除 |
| 图片数量 | 单笔交易仅一张（image_url 是单值字段） |
| 压缩位置 | 前端压缩后上传（减少带宽和存储消耗） |
| 存储容量 | Supabase 免费层 1GB，约可存 3000+ 张压缩图片 |
| 文件类型 | 仅允许 image/jpeg、image/png、image/webp |

### P2-2 年度报告 ✅

**定位**：为用户生成一份可视化的年度消费总结，支持保存为长图分享。

**痛点**：用户积累一年数据后，缺乏直观的回顾工具；手动统计繁琐，缺乏分享属性。

---

#### 核心功能

| 功能点 | 描述 | 优先级 |
|--------|------|--------|
| 年份选择 | 选择目标年份（默认当前年），触发报告生成 | P0 |
| 账本筛选 | 可选择「全部账本」或指定某个账本 | P0 |
| 报告渲染 | 前端渲染隐藏 DOM，包含封面、总览、趋势、排行等板块 | P0 |
| 长图保存 | 点击「保存图片」→ html2canvas 截取报告 DOM → 下载 PNG | P0 |
| 加载状态 | 多 API 聚合加载时显示骨架屏/进度条 | P1 |

#### User Stories

- As a 记账用户, I want 年末查看年度消费总览 so that 了解全年收支全貌
- As a 记账用户, I want 看到月度消费趋势图 so that 发现消费高峰月份
- As a 记账用户, I want 知道钱主要花在哪些分类 so that 优化消费结构
- As a 多账本用户, I want 按账本维度看消费占比 so that 区分不同场景的支出
- As a 分享型用户, I want 将报告保存为一张长图 so that 在朋友圈分享

---

#### 报告板块设计

| 板块 | 内容 | 数据来源 |
|------|------|----------|
| 封面 | 年份 + 用户昵称 + "年度消费报告" + 总收支摘要（一句话） | 聚合 API |
| 年度总览 | 总收入、总支出、结余、结余率（百分比），4 个数字卡片 | 聚合 API |
| 月度趋势 | 12 个月收支双线折线图 + 柱状图（ECharts） | 聚合 API |
| 分类排行 | Top 5 支出分类环形图 + 金额列表 | 聚合 API |
| 消费之最 | 最高单笔消费、最多消费日、最多消费商户 | 聚合 API |
| 账本视角 | 多账本各占支出百分比（仅多账本用户显示） | 聚合 API |
| 成员视角 | 成员消费排名 + "最节俭"和"消费主力"标签（仅多成员账本显示） | 聚合 API |
| 趣味彩蛋 | "你在餐饮上花了 ¥X，相当于 X 杯奶茶"（按 ¥15/杯） | 前端计算 |
| 结尾 | 生成日期 + "记账让生活更清晰" | 前端生成 |

#### 前端长图生成方案

| 环节 | 方案 |
|------|------|
| 报告渲染 | 独立全屏组件 `<AnnualReport>`，渲染在屏幕外（`position:fixed; left:-9999px`） |
| 宽度 | 固定 375px（移动端分享图标准宽度），内容自适应高度 |
| 图表 | ECharts 渲染为 Canvas，html2canvas 可直接捕获 |
| 截图 | `html2canvas(reportRef.current, { scale: 2, useCORS: true })` |
| 下载 | `canvas.toBlob()` → `URL.createObjectURL()` → `<a download>` 触发 |
| 依赖 | `html2canvas`（新增前端依赖，~40KB gzipped） |
| 图标/emoji | 使用系统 emoji，html2canvas 兼容；MUI Icon 使用 SVG 模式 |

**交互流程**：
1. 用户进入报告页 → 选择年份 + 账本 → 点击「生成报告」
2. 前端调用 `GET /api/reports/annual` → 显示骨架屏 → 数据到位后渲染
3. 用户滚动查看报告预览 → 满意后点击「保存为图片」
4. 隐藏 DOM 渲染完整报告 → html2canvas 截图 → 自动下载
5. 截图过程约 2-3 秒，显示进度 toast

---

#### 技术边界

| 维度 | 决策 |
|------|------|
| 是否新建表 | **否** — 纯聚合查询，无持久化需求 |
| 是否新建模块 | **是** — `reports` 模块（NestJS controller + service），单一聚合接口 |
| 前端依赖 | 新增 `html2canvas` |
| 缓存 | 报告数据不缓存（查询即时的聚合数据），保证准确性 |
| 性能 | 聚合查询在 PostgreSQL 内完成（GROUP BY + 窗口函数），不拉数据到应用层计算 |
| 长图 | 不使用 PDF；html2canvas 直接截图 DOM，无分页概念，视觉更丰富 |
| 多账本 | `book_id` 为空时聚合所有账本；报告按板块区分账本维度 |
| 趣味计算 | 奶茶等价等在前端完成（后端只返回原始金额），方便灵活调整文案 |
